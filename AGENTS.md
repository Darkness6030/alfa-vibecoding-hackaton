# Правила проекта хакатона AlfaGen

## Обязательные ограничения

- Программный код, тесты, Dockerfile/Compose и исполняемые скрипты создаются **только DeepSeek-V4-Flash-0731 через настроенное расширение Kilo Code**. Codex и исследовательские сабагенты могут исследовать, читать и создавать документацию, но не подменять обязательную модель при кодогенерации.
- Сохранять endpoint/профиль организаторов; не включать другую модель, Auto Model или fallback. Публичный alias Flash может указывать на другую версию.
- Python и Docker обязательны. Дедлайн **23.09.2026 23:59 MSK**, один участник. Сдаются ZIP, ссылка на version control, URL сервиса, презентация и скринкаст.
- Runtime LLM **пока заглушка по решению участника**. Явно подписывать mock в UI/README/материалах, не выдавать его за реальную генерацию.
- Контракт стенда неизменен: `POST /process`, `{payload: string, payload_id: string}` → `200 {result: string}`. Нельзя переключать направление простым счётчиком запросов: ретраи идемпотентны.
- Ни исходные ПД, ни секреты не попадают в логи/метрики/ошибки/артефакты. Использовать синтетические примеры. Отказ защиты не разрешает выдачу исходного текста как успешной маски.
- Пользовательские изменения Git не откатывать. Не читать секреты Kilo и не менять рабочие подключения ради проверки.

## Перед первой задачей

Прочитать `docs/model-rules.md`, `docs/decisions.md`, `docs/execution-plan.md` и `docs/kilo-start.md`. Детали источников и всех 17 категорий — `docs/requirements.md`; ответы участника — `docs/questions.md`; баллы и сдача — `docs/scoring-and-demo.md`.

Различать обязательные требования, разрешённые исключения участника и наши инженерные решения. Работать небольшими проверяемыми задачами, не писать весь проект за один запрос. После изменения запускать относящиеся к нему проверки и сообщать реальные результаты. После двух неудачных исправлений локализовать причину на минимальном примере. Непроверенные 95%, 1000 RPS и нормативное соответствие не заявлять.

## Развёртывание

`ssh Dental` доступен; участник разрешил остановить существующие контейнеры **на время тестирования**. Делать это только на этапе готового развёртывания, сохранив список работающих сервисов и способ возврата. Не удалять чужие контейнеры/volumes и не использовать prune. На время автоматического прогона разрешён отдельный открытый `/process`; защищённый демо-профиль и внутреннее хранилище остаются ограниченными. Подробности — D07–D08 в `docs/decisions.md`.

Исследовательские рекомендации и источники — `docs/research-model-platform.md`, `docs/research-workflow.md`, `docs/research-architecture.md`. Не перечитывать их целиком для каждой небольшой правки; использовать по задаче.
