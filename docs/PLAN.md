# План разработки модуля защиты персональных данных

## Цель и источники

За два дня создать развёрнутый сервис, который обнаруживает персональные данные (ПД), маскирует их перед передачей в LLM и восстанавливает в ответе. Основной результат хакатона: работающий `POST /process`, измеренное качество, проверенная устойчивость под нагрузкой и ZIP с исходным кодом.

Источники: [краткое описание](description.txt) и [полное ТЗ](ds.pdf), включая приложения A и B на стр. 6–9. Обязательные требования и контракт собраны в [RULES.md](RULES.md). В PDF приведены схема обмена и OpenAPI; архитектурные схемы в наших документах являются предложением реализации, а не схемами организаторов.

Этот документ описывает предстоящую работу, а не достигнутые результаты. [PROGRESS.md](PROGRESS.md) изначально пуст; по мере реализации в нём следует фиксировать выполненные этапы, результаты проверок, принятые решения и блокеры.

## Приоритеты и критерии успеха

| Приоритет | Результат | Критерий готовности |
| --- | --- | --- |
| P0 | Совместимость с проверяющей системой | Строгий контракт `/process`, корректная пара маскирование/демаскирование, безопасные ретраи |
| P0 | Покрытие всех 17 типов ПД | Положительные, отрицательные и смешанные примеры для каждого типа; нет типов без реализации |
| P0 | Качество | Цель ТЗ — 95%; локально отдельно измерены precision, recall, F1 по типам и точное восстановление строк |
| P0 | Приватность | Нет исходных ПД в логах, метриках, ошибках и внешних вызовах; защищённое временное хранение соответствий |
| P0 | Производительность | Прогон около 5 минут при целевых 1000 RPS; зафиксированы latency, ошибки, 429 и потребление ресурсов |
| P0 | Длинные тексты | Проверены входы до 100 000 токенов, границы фрагментов и расход памяти |
| P0 | Настройки потребителей | Разрешение доступа, набор типов ПД и демаскирование управляются отдельно для каждой системы |
| P0 | Сдача | Сервис доступен по переданному URL; подготовлен чистый ZIP; пройдены обе обязательные проверки |
| P1 | Демонстрация интеграции | Показана цепочка «потребитель → защита → LLM/локальная заглушка → восстановление» |
| P2 | Дополнительные баллы | Токенизация/синтетика, комбинированные правила, другие документы, 2000 RPS |

Цель latency из ТЗ — не более 1 секунды. Отдельно показываем p50/p95/p99/max: перцентиль для этого ограничения в ТЗ не задан. Таймаут проверяющей системы 10 секунд не заменяет целевой SLA. Локальные метрики качества не объявляем эквивалентом оценки организаторов без их формулы и эталонных масок.

## Предлагаемый технический подход

Выбор ниже — стартовое решение для двухдневной разработки, а не предписание ТЗ. Проверить его ранним замером и менять только при измеренной необходимости.

- Python + FastAPI/Pydantic для контракта; несколько процессов для CPU-нагрузки.
- Регулярные выражения, контекстные признаки и валидаторы для структурированных данных; локальный NER/словари для ФИО, адресов и организаций. Загрузить модели один раз при старте; не вызывать внешнюю LLM для обнаружения ПД.
- Единый реестр детекторов с результатом `(тип, start, end, confidence, detector_id)`, разрешение пересечений и независимый модуль маскирования.
- Redis как общее краткоживущее хранилище корреляции между процессами; атомарное создание записей, TTL, шифрование чувствительных значений на уровне приложения. Не ограничиваться словарём в памяти одного worker.
- Версионируемый YAML/JSON для политик потребителей; секреты отдельно через окружение/секрет-хранилище.
- Docker Compose для воспроизводимого запуска приложения и хранилища; pytest, инструмент нагрузочного тестирования и метрики Prometheus.

```text
Потребитель / проверяющая система
             |
             v
  POST /process: валидация + политика доступа
             |
             v
  Корреляция (система, payload_id) <--> Redis: зашифрованное состояние + TTL
             |
       +-----+------------------+
       |                        |
       v                        v
  Новый исходный текст     Известный текст / маска
       |                        |
  Детекторы → контекст     Повтор результата либо
  → пересечения → маски   точное восстановление
       |                        |
       +----------+-------------+
                  v
          {"result": "..."}
```

Контрактный endpoint не должен зависеть от доступности LLM: проверяющая система сама присылает маску обратно. Реальный ответ LLM может переставлять или изменять текст, поэтому его восстановление реализуется отдельным внутренним интерфейсом с явным направлением операции и обратимыми идентификаторами; демонстрация может использовать локальную заглушку.

## День 1 — сквозной рабочий сервис

Оценка: 12 рабочих часов, включая небольшой резерв. Этапы выполнять последовательно по зависимостям; к концу дня сервис должен быть уже развёрнут.

### 1. Контракт и неизвестные условия — 1 час

- [ ] Перенести OpenAPI со стр. 6–7 в валидный файл спецификации, исправив только артефакты PDF-форматирования.
- [ ] Выписать вопросы организаторам из RULES.md: эталонные маски, формула качества, доступ проверяющей системы, правила повторов и срок корреляции.
- [ ] Создать небольшую синтетическую выборку со span-разметкой и всеми типами ПД; отделить примеры для настройки от отложенной проверки.
- [ ] Зафиксировать предлагаемые форматы масок как временное решение до уточнения эталонов; изолировать их от детекторов.

Выход: проверяемые схемы обмена и список допущений, без блокировки разработки независимых модулей.

### 2. Каркас, корреляция и первый деплой — 2 часа

- [ ] Реализовать `POST /process`, строгую проверку строковых полей и единый безопасный формат ошибок.
- [ ] Добавить общее хранилище, атомарность, TTL и повторы по содержимому; реализовать таблицу состояний из RULES.md.
- [ ] Добавить настройки потребителя, health/readiness, конфигурацию окружения и контейнерный запуск.
- [ ] Проверить сквозную пару, повторы обоих шагов, одинаковые параллельные запросы и работу через разные процессы.
- [ ] Развернуть раннюю версию; проверить доступность снаружи выбранного окружения.

Выход: минимальный сервис с одним детектором, без потери соответствий между worker-процессами.

### 3. Структурированные ПД — 3 часа

- [ ] Email, телефон, паспорт, водительское удостоверение, ИНН, карта, код подразделения.
- [ ] CVV и ПИН только с достаточным контекстом, чтобы не маскировать произвольные короткие числа.
- [ ] Даты рождения/выдачи: цифровые и текстовые варианты, неоднозначный порядок частей.
- [ ] Проверить разделители, пробелы, регистр, слова «серия»/«номер», пересечения типов и восстановление исходного написания.

Выход: отдельные тесты каждого детектора и общий конвейер замены диапазонов.

### 4. Контекст и оставшиеся категории — 3 часа

- [ ] ФИО, имя держателя карты, гражданство, место рождения, орган выдачи паспорта.
- [ ] Адрес целиком и отдельные компоненты: страна, индекс, город, улица, дом, квартира.
- [ ] Различать сведения о клиенте и публичные упоминания, включая поэта Александра Пушкина и адрес отделения банка.
- [ ] Проверить сложные предложения, несколько лиц, повторяющиеся значения, кириллицу/латиницу и ложные срабатывания на обычном тексте.
- [ ] Сохранить исходные координаты и символы при нормализации для поиска.

Выход: все 17 типов представлены в реализации и в наборе проверок; известные пробелы записаны явно.

### 5. Приватность, политики и базовый замер — 2 часа + 1 час резерва

- [ ] Настроить разрешённые системы, выбор типов и разрешение демаскирования; сверить способ доступа с возможностями проверяющей системы.
- [ ] Шифровать состояние, исключить тела запросов/ответов и ПД из всех уровней логирования.
- [ ] Добавить безопасные события по этапам, найденные типы, latency/RPS/TPS, ошибки и размер хранилища.
- [ ] Провести первый замер качества и нагрузки, выявить главный bottleneck.
- [ ] Протестировать отказ хранилища: сервис не должен возвращать открытые данные вместо маски.

Контрольная точка дня: работающий внешний URL, полный набор типов, обратимость и ретраи, первый отчёт с реальными цифрами.

## День 2 — качество, нагрузка и сдача

### 6. Доведение качества — 3 часа

- [ ] Измерить precision/recall/F1 по типам и в целом на отложенной выборке; отдельно оценить маски и восстановление.
- [ ] Добиваться точного равенства `demask(mask(text)) == text`, включая пробелы, переносы, пунктуацию и Unicode.
- [ ] Исправлять сначала утечки и массовые ошибки типов, затем ложные срабатывания.
- [ ] Проверить сохранение смысла для LLM на нескольких сценариях с синтетическими данными.
- [ ] Если получены эталоны организаторов, согласовать политики маскирования и повторить оценку; иначе явно оставить ограничение совместимости.

### 7. Нагрузка, большие тексты и сбои — 3 часа

- [ ] Увеличивать нагрузку ступенями до 1000 RPS; провести целевой прогон около 5 минут с парами запросов и ретраями.
- [ ] Собирать достигнутый RPS, latency p50/p95/p99/max, TPS, доли 429/4xx/5xx, CPU/RAM и объём состояния; указать оборудование и размеры входов.
- [ ] Проверить текст до 100 000 токенов отдельно и в смешанном профиле; не выдавать результат на коротких строках за результат на длинных.
- [ ] Если нужны фрагменты, использовать перекрытие и единую систему координат; проверить сущности на границах и устранение дублей.
- [ ] Проверить гонки, отключение Redis/детектора, рестарт worker, истечение TTL, потерянный ответ и повтор запроса.
- [ ] Настроить ограничение конкурентности и `429` с `Retry-After`; не поддерживать заявленный RPS массовыми отказами.

### 8. Интеграция и эксплуатация — 2 часа

- [ ] Показать обработку запроса и ответа в цепочке с LLM или честно обозначенной заглушкой.
- [ ] Подготовить README: запуск, переменные окружения, API, ограничения, воспроизведение тестов.
- [ ] Написать отдельную инструкцию настройки потребителя максимум в 5 предложениях.
- [ ] Проверить запуск с чистого окружения, readiness и доступность URL без локальных зависимостей разработчика.

### 9. Заморозка и сдача — 2 часа

- [ ] Завершить изменения функций; выполнить регрессионные проверки контракта, качества и защиты данных.
- [ ] Сформировать ZIP исходников по RULES.md; проверить состав, отсутствие секретов, PDF, зависимостей, дампов и больших моделей.
- [ ] Передать архив на проверку качества кода и URL на нагрузочную проверку по процедуре организаторов.
- [ ] Убедиться в прохождении обеих проверок и сохранять доступность сервиса на время прогона.
- [ ] Подготовить короткое демо: исходный синтетический текст → маска → восстановление; разные политики; публичный адрес; сбой; результаты замеров.

### 10. Резерв — 2 часа

Сначала использовать на ошибки обязательных проверок и нестабильность. Только если P0 закрыт, выбрать одну дополнительную возможность: обратимые токены, комбинации типов, новые документы либо целевой замер 2000 RPS. Полноценный UI и сложную инфраструктуру не включать в критический путь.

## Главные риски и решения

| Риск | Действие |
| --- | --- |
| Эталонный стиль маски неизвестен | Уточнение в начале; сменные политики; не считать пример из OpenAPI универсальным правилом |
| Повтор маскирования принят за демаскирование | Сопоставлять содержимое с сохранённым исходником/маской; проверять гонки и потерянные ответы |
| 1000 RPS с локальным NER недостижимы на доступном CPU | Ранний профиль, ограничение области NER, процессы/реплики, замер на целевом оборудовании |
| Состояние растёт без ограничений | TTL, лимиты, шифрование, измерение памяти; не удалять запись до завершения окна повторов |
| Длинные тексты приводят к утечке на границах | Перекрывающиеся фрагменты, глобальные координаты и специальные проверки границ |
| Условия доступа несовместимы с тестером | Согласовать отдельный профиль/сетевой допуск без изменения JSON-контракта |
| Два дня не позволяют закрыть всё | Сокращать P2 и оформление, а незакрытые P0 фиксировать как ограничения, не как готовые функции |

## Определение готовности

Проект готов к сдаче, когда обязательные результаты из таблицы приоритетов подтверждены проверками, запуск воспроизводим, URL доступен и архив соответствует правилам. В отчёте необходимо отделять измеренные результаты от целей ТЗ и перечислять оставшиеся ограничения. Выполнение требований законодательства и внутренних стандартов банка нельзя объявлять подтверждённым только на основании хакатонного прототипа: сами стандарты и процедура подтверждения в материалах отсутствуют.
