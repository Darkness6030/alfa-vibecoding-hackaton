## 2. Обязательные возможности

Требование ТЗ, разделы 3–5, стр. 2–3:

1. Встраиваться между системой-потребителем и LLM; обнаруживать ПД, маскировать запрос и демаскировать ответ.
2. Поддерживать все категории ниже, расширение детекторов и правил без переработки всего сервиса.
3. Учитывать контекст принадлежности данных человеку; уменьшать ложные срабатывания и сохранять смысл запроса.
4. Настраивать разрешённые системы, включение/отключение доступа, типы обнаруживаемых/маскируемых ПД и возможность демаскирования по системе.
5. Обрабатывать до 100 000 токенов; целевое качество — 95%, latency — не более 1 секунды, нагрузка — 1000 RPS.
6. Обеспечивать шифрование, минимизацию данных, защищённый контур, устойчивость к отказам, безопасные логи и метрики Latency/RPS/TPS.
7. Подготовить краткую инструкцию настройки не более чем в 5 предложениях.

## 3. Контракт обязательного endpoint

Требование ТЗ, приложение A, стр. 6–7:

```http
POST /process
Content-Type: application/json
```

```json
{
  "payload": "Клиент Иванов Иван Иванович, паспорт 4509 123456",
  "payload_id": "8a77d363c7c044b49b41d7b8a448243a"
}
```

Успешный ответ — HTTP 200 и JSON со строковым `result`:

```json
{
  "result": "Клиент И. И. И., паспорт 45** ****56"
}
```

Это пример из OpenAPI, а не полный стандарт маскирования всех типов. Нельзя утверждать, что произвольные звёздочки, инициалы или токены совпадут с эталонными масками.

- `payload` и `payload_id` — обязательные строки; ограничение `payload_id` форматом UUID в ТЗ отсутствует.
- Первый запрос с новым `payload_id`: маскирование исходной строки и сохранение соответствия.
- Второй запрос с тем же `payload_id`: в `payload` приходит ранее возвращённая маска; вернуть исходную строку.
- Ответ об успешной обработке: `{"result": "..."}`. Не требовать дополнительных полей `mode`, `system_id`, `mapping` или другого endpoint от тестера.
- Описаны статусы `429`, `4XX`, `5XX`; схема тела ошибки не определена. Решение проекта: безопасная строка в `result` без входных данных плюс соответствующий HTTP-статус.
- HTTP и HTTPS допускаются; самоподписанный сертификат принимается тестером с `ssl_verify=false`. Решение проекта: использовать HTTPS для защиты канала; не переносить отключение проверки сертификата в собственные исходящие клиенты.

```text
Проверяющая система                POST /process               Состояние
         |                              |                         |
         |-- {исходник, id=A} ---------->|-- атомарная запись ---->|
         |<--------- {result: маска} ----|                         |
         |                              |                         |
         |-- {та же маска, id=A} ------->|-- чтение соответствия -->|
         |<------ {result: исходник} ----|                         |
```

Самопроверка формата из приложения B (стр. 9): `https://process-test.holydev.space/process`. Этот адрес указан в исходнике, его доступность в рамках подготовки документов не проверялась. Он демонстрирует формат, а не качество обнаружения или эталонные правила маскирования; для проверки использовать только синтетический текст.

## 4. Корреляция, повторы и обратимость

ТЗ одновременно задаёт двухшаговый протокол и требует идемпотентности при ретраях (стр. 6, 8). Поэтому **нельзя переключать направление только по количеству обращений**.

Решение проекта: ключ состояния `(идентификатор разрешённой системы, payload_id)`, атомарное создание записи и сравнение содержимого запроса с сохранённой парой. Идентичность системы устанавливается доверенным механизмом доступа, а не произвольным значением из тела запроса.

| Состояние | Входящий payload | Действие |
| --- | --- | --- |
| Записи нет | Новый исходный текст | Обнаружить, замаскировать, сохранить соответствие до отправки HTTP 200 |
| Запись есть | Равен исходному тексту | Вернуть ту же маску: это повтор прямого шага |
| Запись есть | Равен сохранённой маске | Вернуть точный исходник: обратный шаг или его повтор |
| Запись есть | Исходник и маска совпадают | Вернуть неизменный текст; оба направления дают один результат |
| Запись есть | Не совпадает ни с одним | Контролируемый конфликт, например HTTP 409; не перезаписывать запись |
| Операция ещё выполняется | Параллельный запрос с тем же ключом | Дождаться результата в пределах бюджета либо вернуть повторяемый отказ; не создавать независимую запись |

HTTP 409 и стратегия параллельного ожидания — решения проекта, не явно заданные коды ТЗ. Проверка точного равенства подходит для проверяющего endpoint, где возвращается именно наша маска. Для изменённого ответа LLM необходим другой внутренний интерфейс и восстановление по уникальным токенам/соответствиям; возврат всего сохранённого исходника не заменяет обработку произвольного ответа LLM.

Правила состояния:

- Сохранять данные, необходимые для восстановления и ретраев, в зашифрованном виде; не дублировать исходник в нескольких хранилищах.
- Минимальная логическая запись: владелец, версия политики, срок жизни, защищённое соответствие исходник/маска либо неизменяемый шаблон и исходные фрагменты. Для поиска совпадений можно использовать HMAC; простой хеш низкоэнтропийных ПД не считать защитой.
- Обеспечить общее состояние всех worker/реплик и атомарность публикации маски. Не отдавать успешную маску, если запись для обратной операции не сохранена.
- Не удалять соответствие сразу после первого демаскирования: ещё возможен повтор обратного запроса.
- TTL должен покрывать пару запросов и окно повторов, но не быть бессрочным. Конкретное значение согласовать/проверить нагрузкой, а не выдавать за требование ТЗ.
- После удаления записи протокол не позволяет надёжно отличить новую строку от старой маски. Это ограничение нужно явно учитывать; срок жизни и повторное использование id требуют уточнения.
- При конфликте политики использовать сохранённую версию преобразования, но заново проверять текущее право системы на доступ и раскрытие.

## 5. Правила работы с текстом

Решения проекта для выполнения требований к качеству и точному восстановлению:

1. Исходный текст неизменяем; нормализацию использовать только для обнаружения с отображением координат на оригинал.
2. Договориться о единой системе смещений, например индексах Unicode-символов Python, и полуинтервалах `[start, end)`; не смешивать байты, символы и токены.
3. Детекторы возвращают кандидатов; общий resolver устраняет пересечения детерминированно с учётом типа, контекста и уверенности.
4. Заменять непересекающиеся диапазоны справа налево либо собирать строку из исходных фрагментов. Не использовать глобальный `replace` по значению.
5. Сохранять пробелы, переносы, регистр, пунктуацию и исходное написание при демаскировании; эталон для обратного шага — точное равенство исходной строке.
6. При токенизации гарантировать уникальность маркеров в пределах контекста, защиту от коллизий с входным текстом и изоляцию между системами. Не раскрывать неизвестные/чужие токены.
7. Для длинных текстов проверять сущности на границах фрагментов, координаты, дубли и память. Не усекать вход молча.

Сохранение местоположения знаков требуется при демаскировании (стр. 3); одинаковая длина исходника и маски не задана, а пример OpenAPI сокращает ФИО.

## 6. Безопасность, настройки и наблюдаемость

Требования ТЗ: защищённый контур, шифрование, минимизация данных, отсутствие утечек, подробное логирование этапов и выявленных типов ПД. Подробные логи не означают запись найденных значений.

Решения проекта:

- Не отправлять исходные ПД внешним LLM/API, телеметрии или системам отладки; использовать локальные детекторы. Для разработки и демо — синтетические данные.
- Не записывать `payload`, `result`, исходные фрагменты и таблицы соответствий в логи, трассировки, метрики и исключения. Проверить также reverse proxy, middleware, ошибки валидации и клиент Redis.
- Логировать безопасный внутренний request id, этап, типы и количество найденных сущностей, версию политики, время и код результата. Произвольный входной `payload_id` не копировать в логи как заведомо безопасное значение.
- Не помещать произвольные id, значения ПД и тексты в labels метрик. TPS измерять по явно выбранному токенизатору; оценку количества токенов обозначать как оценку.
- Шифровать чувствительное состояние проверенной библиотекой с аутентификацией шифротекста; ключи держать отдельно от данных и исходников. Ограничить доступ к Redis и его дампам/резервным копиям.
- При отказе обязательного детектора или хранилища возвращать контролируемую ошибку; не выдавать непроверенный исходник как успешно защищённый результат. Упрощённый режим допустим только при сохранении покрытия активной политики.
- Проверять конфигурацию до применения. Недоступная/отключённая система не получает обработку; запрет демаскирования должен реально предотвращать раскрытие.
- Для тестера предусмотреть разрешённый профиль без изменения JSON-контракта. Заголовки авторизации не указаны в ТЗ; нельзя вводить обязательный API-ключ без согласования способа его передачи.

Логическая схема политики, не новый API-контракт:

```text
ConsumerPolicy
  system_id              доверенный идентификатор потребителя
  enabled                разрешение доступа
  detect_types           типы для обнаружения
  mask_types             типы для маскирования, подмножество detect_types
  demask_enabled         разрешение раскрытия
  masking_profile        стратегия представления маски
  version                версия правил
  combination_rules      дополнительные условия сочетания типов (P2)
```

Для профиля проверки включить все обязательные типы и демаскирование. Конфигурация не должна незаметно снимать защиту обязательных категорий.

## 7. Нагрузка и условия автоматической проверки

Требования приложения B, стр. 8:

| Параметр | Условие |
| --- | --- |
| Основной прогон | По всем категориям, около 5 минут, целевые 1000 RPS; элементы датасета переиспользуются |
| Latency | Цель не более 1 секунды; в инструкции к проверке названа ориентиром, а не жёстким таймаутом |
| Таймаут запроса | 10 секунд; более долгий ответ считается неответом |
| Повторы | До 2 ретраев, то есть до 3 попыток каждого запроса |
| Перегрузка | `429` допустим; учитывается `Retry-After`, устойчивые 429 означают недостижение нагрузки |
| 429 на прямом шаге | Если не проходит после повторов, обратный шаг для элемента не запрашивается |
| 429 на обратном шаге | Учитывается, проверка продолжается |
| Остановка | После 5 невалидных запросов подряд; 429 не увеличивает и не сбрасывает счётчик, успех сбрасывает |
| Маскирование | Сравнение с эталонной маской: нормированное span-based расстояние Левенштейна, диапазон `[0..1]` |
| Демаскирование | Сравнение с исходной строкой из датасета |

Не считать 1000 RPS количеством завершённых пар: пара требует два HTTP-запроса, а повторы увеличивают их число. Формула нормировки/агрегации качества, направление шкалы и преобразование в требование 95% не приведены. Порог 95% нельзя автоматически трактовать как F1 либо как конкретное значение расстояния.

Локальные проверки должны охватывать контракт, все типы, отрицательные примеры, формат масок, точное восстановление, ретраи обоих шагов, гонки, изоляцию систем, TTL, смену политик, отказ зависимостей, отсутствие ПД в телеметрии и входы до 100 000 токенов. Для отчёта сохранять параметры оборудования, набор/размеры синтетических входов, фактический RPS, перцентили latency, ошибки и ресурсы.

## 8. Сдача и дополнительные возможности

Обе автоматические проверки обязательны (стр. 5): качество кода после загрузки ZIP и нагрузочное тестирование развёрнутого сервиса. Без любой из них решение не учитывается.

В ZIP включать только исходный код решения и необходимые текстовые файлы запуска/конфигурации без секретов. Исключить датасеты, дампы, архивы, медиа, бинарники, зависимости, модели и сборки; не включать `docs/ds.pdf`. Исключить каталоги `node_modules`, `.venv`, `venv`, `env`, `target`, `build`, `dist`, `out`, `bin`, `obj`, `.git`, `.idea`, `__pycache__`, `coverage`. Структура архива должна быть понятной, размер разумным. Доступность URL сохранять на момент прогона.

Дополнительные плюсы из раздела 6 (стр. 4), после обязательной части:

- Токенизация/детокенизация или синтетические замены.
- Выбор вида маскирования/токенизации по системе.
- 2000 RPS при latency не более 1 секунды.
- Другие удостоверяющие личность документы, кроме паспорта РФ.
- Настраиваемое маскирование по сочетанию типов, например ПИН вместе с номером карты. Это дополнительный режим, не основание отключать базовое покрытие CVV/ПИН по умолчанию.

## 9. Вопросы, которые материалы не разрешают

1. Какие точные правила эталонных масок применяются к каждому типу? Пример ФИО/паспорта не описывает остальные категории и вариации.
2. Как вычисляются span-based расстояние, итоговая оценка и требование 95%? Доступны ли эталонные примеры и код метрики?
3. Какой профиль размеров входов и какое оборудование соответствуют SLA? Требуются ли 1000 RPS одновременно на текстах по 100 000 токенов, какой токенизатор используется?
