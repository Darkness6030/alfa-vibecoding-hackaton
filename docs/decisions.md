# Принятые решения и границы реализации

Дата: 22.09.2026. Основания: [ответы участника](questions.md), [требования](requirements.md), [критерии и демо](scoring-and-demo.md), три документа `research-*.md`. Решения можно менять при измеренном провале, сохраняя контракт; ниже нет обещаний достигнутой производительности.

## D01. Кто создаёт код

**Решено участником:** Python, Docker; весь программный код, тесты, Dockerfile, Compose и исполняемые скрипты создаёт предоставленная DeepSeek-V4-Flash-0731 через Kilo. Codex/исследовательские сабагенты создают документацию, анализируют требования и результаты. Корневой `AGENTS.md` — инструкция, не код проекта. Подключение Kilo не перенастраиваем, другую модель для кодирования/ревью с исправлениями автоматически не выбираем.

## D02. Стек и объём

**Инженерное решение для старта:** один Python-проект, FastAPI/Pydantic, Uvicorn, Redis для общего краткоживущего состояния, локальные детекторы, Prometheus-совместимые метрики, pytest; Docker Compose. Простая HTML-страница для демо допустима без отдельного SPA, node toolchain и базы пользователей. README ведётся с первого этапа.

Выбор FastAPI/Redis и подходы к измерениям обоснованы в [исследовании архитектуры](research-architecture.md). Redis нужен для согласованного состояния нескольких процессов, а не как основание немедленно запускать много реплик. На одном сервере начать с 1 worker и сравнить 2/4; 8 vCPU не означают, что 8 моделей/процессов эффективнее. Kubernetes, SQL-БД, очередь задач и микросервисный парк в базовый объём не входят.

## D03. Детекция

Комбинация детерминированных паттернов, контекста/словарей и локального русского NER. Первый кандидат для замера — Slovnet/Navec через Natasha; NER покрывает лишь часть задачи и не заменяет отдельные правила всех 17 категорий. Загрузка весов в Docker при сборке/подготовке с фиксацией версии/контрольной суммы; веса не включать в ZIP.

В течение первого короткого эксперимента модель-разработчик измеряет качество на синтетических смешанных примерах и стоимость CPU. Если библиотека/зависимости не подходят, упрощается конкретный компонент с явным отчётом потерь, а не незаметно вырезаются ФИО/адреса. Внешнего генеративного LLM-вызова в `/process` нет: он не нужен для парной проверки и привязывал бы скорость/приватность к внешнему сервису.

## D04. Маскирование

Основной режим — **непрозрачные типизированные токены**: тип сохраняет роль значения для LLM, непредсказуемый идентификатор не содержит исходное значение и не позволяет восстановить его без защищённого соответствия. Конкретный синтаксис, достаточную энтропию и правила экранирования создаёт модель; обязательны отсутствие коллизий с исходным текстом и изоляция контекстов. Одинаковую сущность внутри одной сессии можно обозначать одинаково, но не создавать глобально устойчивый идентификатор человека между потребителями.

Второй конфигурируемый режим — полное скрытие чувствительного диапазона с сохранением согласованных разделителей. Токенизация лучше подходит для демо с изменённым LLM-ответом; статическая маска без уникального маркера может быть неоднозначна для такого ответа. Не обещать универсальную обратимость второго режима вне точной `/process` пары. Частичные маски, оставляющие цифры карты/документа, не выбираем по умолчанию только из-за единственного примера PDF.

Критерии прямо засчитывают токенизацию; участник разрешил самостоятельно выбрать формат. Совместимость с неизвестной автоматической span-метрикой остаётся риском. Формат конфигурируем, первую внешнюю проверку провести рано; не подгонять всю архитектуру под догадку о метрике.

## D05. Идемпотентность и срок состояния

Ключ состояния: серверный namespace прогона + доверенный consumer + `payload_id`. В режиме проверки consumer фиксирован конфигурацией, не берётся из произвольного клиентского поля. Параметры преобразования пары неизменны после успешной публикации, включая версию правил маскирования. Авторизация проверяется заново на каждом запросе по актуальной конфигурации: отключение потребителя или отзыв права демаскирования действует и на уже созданные пары. Старое состояние не обходит отзыв доступа.

| Состояние и вход | Действие |
| --- | --- |
| Новый id, обычный исходный текст | Обнаружить/замаскировать, атомарно записать готовую пару, затем вернуть маску |
| Известный id, исходный текст совпал | Вернуть ту же сохранённую маску, независимо от количества предыдущих запросов |
| Известный id, маска совпала | Вернуть точно восстановленный исходник при разрешённом демаскировании |
| Оригинал = маска (ПД не обнаружены) | Возвращать ту же строку при повторах, не переключать режим |
| Известный id, иной текст | `409`, без утечки состояния/исходника |
| Истёкшее состояние, распознанный собственный токен | Контролируемая ошибка, не выдавать маску за успешное демаскирование |
| Хранилище недоступно | Контролируемая ошибка без `200` с оригиналом и без отправки его в LLM |

При гонке запись создаётся атомарно; проигравший читает опубликованное состояние и применяет ту же таблицу. Маску нельзя вернуть до сохранения соответствий. После обратного шага состояние сохраняется до TTL для повторов; ретраи не продлевают TTL бесконечно.

Предварительный TTL — **15 минут**, отдельные настройки лимита записей/байтов и более длинного маркера недавно истёкшего id без исходного текста. Это наше значение для пятиминутного прогона, не SLA организаторов. На 1000 HTTP RPS и среднем количестве двух запросов на пару — до 150 000 новых пар за 5 минут; если 1000 означает пары/сек, до 300 000. Память измеряется по реальной средней записи, не по одному примеру; большие тексты и высокая частота проверяются отдельно.

Ограничение протокола: когда состояние и tombstone исчезли, произвольная статическая маска неотличима от нового исходного текста; абсолютная гарантия демаскирования после неограниченной паузы невозможна. Это документируется, а не скрывается. Namespace меняется перед новым прогоном только после завершения старого; во время активных пар не терять правила преобразования и ключи, нужные для восстановления. Это не мешает немедленному отзыву доступа по текущей конфигурации.

## D06. Две границы API

- `/process` — точный протокол стенда, без дополнительных обязательных полей и без вызова LLM.
- Демонстрационный proxy endpoint — отдельный сценарий: потребитель → детекция → токены → LLM → проверка ответа → детокенизация → разрешённый потребитель. Он использует то же ядро и политики, не дублирует детекторы.

LLM получает только защищённый текст. Системная инструкция просит не менять токены, но это не гарантия: неизвестные/повреждённые токены не восстанавливаются наугад. Утрата токена не должна заставлять сервис вернуть весь исходный запрос вместо ответа модели. Исходный текст видит авторизованный потребитель; безопасный диагностический показ сетевого тела строится только на синтетических примерах.

**Решение участника после исследования:** пока использовать заглушку LLM. Реализовать локальный детерминированный mock за интерфейсом адаптера, явно подписанный в UI, README, презентации и скринкасте. Он возвращает изменённое окружение/порядок целых токенов, чтобы проверять настоящую детокенизацию, а не только echo. Отдельные тестовые режимы имитируют таймаут/повреждённый токен. Это не блокирует текущую реализацию; качество генерации реальной LLM и живая интеграция не проверены и остаются ограничением относительно критерия демо-прокси. Адаптер настоящего API — будущая замена без изменения ядра. Код заглушки и адаптера пишет обязательная модель; ключи Kilo не извлекать.

## D07. Доступ и шифрование

Два именованных профиля конфигурации:

1. **demo-secure:** системы с ключами/allowlist, индивидуальные политики, запрет чужого демаскирования; используется для демонстрации безопасности.
2. **evaluation-open:** по разрешению участника входной `/process` временно открыт проверяющей системе, сопоставлен одной тестовой политике; отдельное пространство состояния, ограниченный срок и ресурсы. Административные функции, Redis и чувствительная диагностика не становятся публичными.

Открытый профиль не даёт той же гарантии аутентификации, что защищённый: это явное исключение для проверки. Использовать синтетические данные, не объявлять такой endpoint банковским production-контуром. Для демо-прокси сохраняется защищённый режим. Можно использовать отдельные экземпляры API из одного образа с разными профилями, не устраивая общую глобальную кнопку «выключить безопасность».

Redis доступен только внутри Docker-сети; исходные соответствия шифруются с аутентификацией, ключ вне репозитория. HTTP допускается стендом, но плановый вход — HTTPS по IP с self-signed сертификатом, который стенд поддерживает. Если сдаётся HTTP, честно обозначить отсутствие транспортного шифрования; это не выполнение исходного требования. Минимальный TLS-терминатор допустим, не разрабатывать собственную криптографию.

## D08. Dental и развёртывание

Read-only осмотр 22.09.2026: Linux x86_64, **8 логических CPU, 11 GiB RAM**, на текущем сервере ~6,6 GiB доступно; диск 96G, свободно 53G; Docker 29.7.0; **22 работающих контейнера**. CPU-модель, GPU и гарантированная доля vCPU не измерялись. Это снимок состояния до остановки сервисов, не гарантированный бюджет после неё.

Участник уже разрешил остановить все существующие контейнеры **на время тестирования**. Сейчас они не останавливались. Перед окном развёртывания модель через Kilo должна:

1. Сохранить список работающих контейнеров/Compose-проектов и порядок восстановления, убедиться в готовности образа и свободном порте.
2. Остановить прежние контейнеры без удаления volumes/данных, затем поднять хакатон под отдельным Compose project name.
3. Проверить health, прямой/обратный запрос, доступ по IP извне и ресурсные лимиты; только потом запускать нагрузку.
4. При провале откатить свой deployment и вернуть именно ранее работающие контейнеры. Не выполнять `prune`, удаление volumes или очистку чужих проектов.
5. После завершения официального окна вернуть предыдущие сервисы; сроки не угадывать и не гасить оцениваемый endpoint до окончания проверки.

Первую разработку/сборку проводить локально. Ранний smoke на Dental организовать так, чтобы не останавливать соседние сервисы надолго до готовности приложения.

## D09. Метрики и бонусы

Измерять latency отдельно для детекции, `/process` и полного proxy round-trip: время внешней генерации не приписывать детектору и не скрывать. RPS предложенный/успешный, ошибки, 429, p50/p95/p99/max, память и CPU фиксировать отдельно. Для TPS явно указывать локальный токенизатор; техническую оценку объёма текста не выдавать за billed tokens внешней модели.

Цель исходного ТЗ — 1 с/1000 RPS, критериев — 0,5 с/1000 RPS; рабочая цель более строгая. Перцентиль официально не указан, поэтому показываем все основные перцентили, не объявляем p95 заменой официального требования. 2000 RPS — бонус после измерения.

Три предпочтительных дополнительных сценария: токенизация, настройка вида маскирования по системе, правило сочетания типов. По умолчанию CVV/ПИН защищаются; ослабляющее правило сочетания демонстрируется только как явно выбранная политика на синтетическом тексте. Отсутствие production-ready инфраструктуры допустимо; отсутствие контроля утечек — нет.
