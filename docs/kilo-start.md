# Начало реализации в Kilo Code

Это готовые инструкции для обязательной модели, не программный код. Исследование выполнено; ответы есть; новых согласований для рутинного выбора библиотек/структуры не требуется. Работать через существующий профиль **DeepSeek-V4-Flash-0731**. Проверки производительности/качества ещё не выполнялись: исходников приложения пока нет.

## 1. Стартовый промпт

Вставить в новую задачу Kilo в этом репозитории:

> Ты реализуешь проект хакатона AlfaGen через обязательную DeepSeek-V4-Flash-0731. Сохрани текущие настройки модели и провайдера. Прочитай AGENTS.md, docs/model-rules.md, docs/decisions.md, docs/requirements.md и docs/execution-plan.md. Пользователь уже ответил на вопросы; рутинные решения принимай самостоятельно в этих границах. Стек Python/Docker, runtime LLM пока явно обозначенная заглушка. Сначала коротко назови контракт, важнейшие ограничения и текущий этап. Затем выполни только K1: воспроизводимый Docker-каркас API, валидацию официального `/process`, health и README. Временное отсутствие детекторов явно обозначь и не объявляй echo готовым маскированием. Выполни проверку сборки/запуска и формата ответов. Не трогай Dental на этом этапе, не откатывай исходные изменения Git. Заверши списком созданных файлов, фактически выполненных проверок, ограничений и точной следующей задачи K2.

Если модель не прочитала документы или пропустила контракт, сначала исправить контекст, затем код. Не тратить время на самопрезентацию модели: её текстовый ответ не подтверждает точный backend. При работающих tools сразу переходить к реализации; отдельный capability probe из исследования нужен только при сомнениях в чтении/редактировании/запуске тестов.

## 2. Карточки следующих задач

Давать одну карточку за раз; большой этап разбивать на 2–3 небольших, сохраняя общие инварианты. Общий финал каждого запроса: «Проверь фактический результат, покажи команды/результаты, не ослабляй тесты, отметь ограничения и обнови короткое состояние. Не меняй модель/провайдера».

| K2a | Создай единое ядро интервалов/токенов и точного восстановления, API детектора; один временный детектор только для проверки механики | Unicode/emoji, пробелы, повторные значения, коллизия токена, точное восстановление |

Бонусные режимы выполнять лишь после обязательной базы: токенизация уже есть; выбор маски и правило сочетания добавлять как небольшие проверяемые настройки. Не затягивать подготовку презентации и видео после заморозки в 16:00 23 сентября.

## 3. Что держать в контексте текущей задачи

- Конкретный ID этапа, требование и ожидаемый результат.
- Файлы текущего компонента, публичные интерфейсы и связанные тесты.
- Последний проверенный commit, точный вывод упавшей команды, если есть ошибка.
- Ограничения: обязательная модель, Python/Docker, секреты/ПД, неизменность `/process`.

Не прикладывать весь репозиторий, PDF, логи всех итераций и результаты всех исследований к каждой правке. Для новой сессии достаточно короткой передачи состояния с ссылками; попросить модель прочитать нужные файлы фактически.

## 4. Правило завершения этапа

Этап не завершён словами модели «готово». Нужны наблюдаемое поведение, фактические проверки и отсутствие известного нарушения обязательного контракта. Если измерение не выполнено, написать «не измерено», а не прогноз. Рабочий commit создавать с осознанным выбором файлов: начальный index уже содержит пользовательские staged-удаления.

После двух неудачных исправлений одного дефекта запросить минимальный пример и причинный разбор; затем одна проверяемая правка. Дополнительную возможность можно отложить, обязательное требование — только явно обозначить как непокрытый риск, не скрывать.
