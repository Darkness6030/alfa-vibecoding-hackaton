# K9: Нагрузочный отчёт

Дата: 22.09.2026. Сервер Dental (8 logical CPU, 11 GiB RAM). Профиль `evaluation-open`, 1 Redis. Нагрузочный сценарий: `benchmarks/load_test.py` (httpx async, пары mask).

## Результаты (30 с, уникальные тексты)

| Workers | Success RPS | p50 | p95 | p99 | max | Ошибки |
|---------|------------|-----|-----|-----|-----|--------|
| 1 | 163 | 157 ms | 254 ms | 528 ms | 3542 ms | 0 |
| 2 | 224 | 120 ms | 234 ms | 258 ms | 1264 ms | 0 |
| 4 | 267 | 118 ms | 278 ms | 471 ms | 1311 ms | 0 |

Повторные тексты (repeat): 1 worker ~155 RPS, 2 workers ~283 RPS, 4 workers ~270 RPS.

## Узкое место: Redis round-trip

- CPU сервера во время нагрузки ~14% (idle 82%) — CPU не ограничение.
- Каждый запрос `/process` делает Redis `SET NX` (repeat — `SET NX` + `GET`); все workers делят один Redis.
- Масштабирование сублинейное (163→224→267 RPS): добавление workers даёт всё меньше, т.к. узкое место — задержка Redis, а не CPU.
- **Вывод:** узкое место — Redis round-trip latency. Для роста RPS нужен либо локальный кэш/батчинг, либо более быстрый доступ к состоянию, либо асинхронные handlers.

## Найденный критический дефект

**Эфемерный ключ шифрования на worker.** Без общего `ALFAGEN_ENCRYPTION_KEY` каждый worker генерирует свой ключ; кросс-worker демаскирование падает с 503 (`InvalidToken`). Исправлено: общий ключ в compose + очистка Redis при смене ключа. Это критично для multi-worker.

## Ограничения

- Нагрузочный клиент (httpx) при concurrency 40 даёт `conn`-ошибки (клиентское ограничение пула соединений); чистые числа получены при concurrency 30.
- `offered_rps` — метка; фактический rate определяется concurrency.
- 1000 RPS не достигнуто; цель критериев 0.5 с/1000 RPS не подтверждена.
- Метрики RAM/CPU: CPU ~14%, память не измерена точно.
- Официальный evaluator не запускался.
