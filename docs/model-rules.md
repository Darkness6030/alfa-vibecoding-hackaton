# Строгие инструкции модели-разработчику

Статус: актуализировано 22.09.2026 по ответам участника, двум PDF критериев и трём исследованиям. Это проектные правила для DeepSeek-V4-Flash-0731 в Kilo Code. Полный реестр решений — `docs/decisions.md`; код, тесты и инфраструктуру создаёт только обязательная модель. Codex и исследовательские сабагенты готовят документацию. Runtime LLM пока заменена явно подписанной заглушкой по решению участника.

## 1. Задача и порядок чтения

Создай модуль защиты персональных данных между системой-потребителем и LLM. Обязательны идентификация всех 17 категорий из ТЗ, маскирование, точное демаскирование, политики потребителей, безопасность, наблюдаемость и работающий контракт проверки.

Перед работой прочитай:

1. `docs/questions.md`: ответы участника и нерешённые ограничения.
2. `docs/requirements.md`: полный реестр, контракт, источники и неоднозначности.
3. `docs/ds.pdf`: первоисточник, особенно страницы 6–9; `docs/description.txt`.
4. Этот файл, `docs/decisions.md`, `docs/execution-plan.md` и текущую задачу из `docs/kilo-start.md`.
5. `docs/scoring-and-demo.md`: доказательства по критериям и обязательные материалы сдачи.

Не подменяй исходное ТЗ пересказом. При расхождении зафиксируй проблему; рутинное инженерное решение принимай самостоятельно по `decisions.md`, как разрешил участник. Критические неизвестные не выдавай за подтверждённый факт. Различай требование организаторов, требование участника, принятое инженерное решение и пока непроверенную гипотезу.

## 2. Обязательная модель и платформа

- Требуемое участником имя модели: **`DeepSeek-V4-Flash-0731`**, без молчаливой замены другой версией или похожим названием.
- Используй уже настроенное расширение Kilo Code; локально найдена версия 7.7.6 с CLI backend. Сохраняй профиль организаторов. Публичный alias `deepseek-v4-flash` уже может указывать на V4.1; не перенастраивай endpoint и не включай другую fallback/auto-модель. После смены режима проверяй модель. Источники: `research-model-platform.md`.
- Не выдумывай размер контекста, лимит ответа, поддержку tool calling, параллельных инструментов, structured output, reasoning-параметров, API-совместимость, цену и скорость этой версии. Не переноси характеристики V3/R1/другой Flash-модели на этот идентификатор.
- Различай модель, с помощью которой пишется код, и модели, используемые готовым сервисом. Обязательность первой сама по себе не доказывает обязательность вызова LLM на каждый запрос `/process`.
- Карточка точной модели описывает reasoning `low/high/max`, но поддержка параметров и лимиты endpoint организаторов не подтверждены. Сначала текущие рабочие настройки; high/max — только если доступны и оправданы задачей. Не копируй 384K output локального инференса в Kilo. Возможности инструментов проверь коротким циклом чтение → правка → реальный тест. Источники и ограничения — `research-model-platform.md`.
- Ответы получены, подготовка завершена. В Kilo переходи к последовательной реализации Python/Docker по этапам. Переполнение контекста решай краткой передачей состояния и новой задачей той же модели, не сменой модели. Проверяй отдельно модель compaction/вспомогательных агентов; при неизвестных лимитах не рассчитывай на auto-compaction.

## 3. Контракт нельзя менять ради удобства

- Реализуй `POST /process`, вход `{"payload": string, "payload_id": string}`, успешный выход `200 {"result": string}`.
- Не добавляй обязательные поля, другой путь или отдельный режим маскирования в запрос проверяющего стенда. По решению участника `/process` на время теста работает в отдельном `evaluation-open` профиле. Остальные маршруты и демонстрационный защищённый профиль сохраняют ограничения доступа.
- Новый id с исходным текстом возвращает маску и сохраняет соответствие; обратный запрос с той же корреляцией и ранее возвращённой маской возвращает исходную строку.
- Не реализуй направление как `число_вызовов % 2` или «id найден — всегда вернуть оригинал». Повторы после потери ответа не должны менять результат операции или раскрывать исходный текст.
- Реализуй D05: атомарное неизменяемое состояние по namespace/consumer/id, распознавание повторов по содержимому и конфликт `409`. TTL по умолчанию 15 минут настраивается, память ограничена, состояние общее для workers. Параметры преобразования сохраняются для пары, но действующее разрешение потребителя/демаскирования проверяется каждый раз; отзыв доступа действует немедленно. Не удаляй соответствие сразу после первого демаскирования: проверяющий клиент может повторить запрос.
- Для одновременных запросов одного id, нескольких workers/реплик, просроченного состояния, постороннего текста с известным id и повторного прогона опиши и проверь поведение.
- Не возвращай сохранённые ПД только на основании знания `payload_id`; проверяй точное содержимое и допустимый сценарий. В `demo-secure` дополнительно проверяй потребителя. `evaluation-open` — явное временное исключение аутентификации для синтетической проверки; не обещай ему те же гарантии.

## 4. Обработка текста и качество

- Покрой PD01–PD17 из `requirements.md`, а не только удобные для регулярных выражений типы.
- Отделяй обнаружение сущности, определение её персонального контекста, разрешение пересечений, политику и преобразование текста. Это предлагаемая граница модулей, не требование конкретного фреймворка.
- Сохраняй исходную строку без потерь на уровне символов. Если нормализация помогает поиску, сохраняй отображение позиций на оригинал. Не нормализуй регистр, пробелы, переносы, «ё» или Unicode в восстанавливаемом результате.
- Для совпадений используй явно определённые интервалы и единицы индексации. Разрешай пересечения детерминированно, не допускай двойного маскирования и смещения соседних участков.
- Не считай все числа, имена и топонимы ПД без контекста. Не создавай глобальное исключение «Пушкин никогда не ПД»: пример поэта не распространяется на однофамильца-клиента.
- Проверяй контекстные исключения, разные регистры, форматы дат, текстовые даты, слова между серией и номером, смешанные категории, повторяющиеся значения и пунктуацию.
- Базовый режим — непрозрачные типизированные токены, второй режим — конфигурируемая полная маска. Выбор участник разрешил; критерии засчитывают токенизацию и вариации. Пример частичной маски не обязателен. Не обещай конкретный автоматический балл без прогона; для изменённого ответа LLM используй токены, а ограничения статических масок укажи.
- Обратная проверка должна восстанавливать оригинал точно. Отдельно проверь демаскирование в изменённом ответе LLM-заглушки: возврат целиком сохранённого запроса его не реализует.
- Проверка больших текстов не должна молча обрезать вход, терять сущности на границах частей или ухудшать формат восстановления.
- Не обучай решение на скрытом тесте и не подставляй ответы по известным примерам. Локальные тесты должны проверять общие правила.

## 5. Безопасность и отказоустойчивость

- Не отправляй исходные защищаемые данные внешним сервисам вне разрешённого контура. Для разработки и демонстрации используй синтетические примеры.
- Не записывай payload, оригиналы сущностей, таблицы соответствий, секреты, CVV/ПИН и чувствительные тела ответов в логи, метрики, трассировки, ошибки, crash-reporting и отладочные дампы.
- Журналируй этап, технический идентификатор, типы/количество сущностей, длительность и безопасную категорию ошибки. Не используй содержимое текста или высококардинальные идентификаторы как labels метрик.
- Минимизируй хранимые сведения, задай ограничение памяти и согласованный TTL. Защити необходимые обратимые соответствия шифрованием; ключи храни отдельно от исходников. Не называй Base64 шифрованием, а обратимую замену анонимизацией.
- При отказе обязательной защиты не пересылай исходный текст в LLM. Деградация должна сохранять безопасность: допустимая локальная защита с известными свойствами либо контролируемый отказ.
- Ограничивай очередь/конкурентность и возвращай контролируемый `429` с корректным `Retry-After` при перегрузке. Постоянные `429` не считаются выполнением RPS.
- Не обещай соответствие законодательству, ЦБ или стандартам Банка без доступных требований и проверки. Пробелы документируй.

## 6. Проверяемый цикл разработки

Работай задачами на 25–50 минут с одним наблюдаемым результатом; основания и шаблоны в `research-workflow.md`. После двух неудачных попыток исправления сузь проблему до воспроизводимого случая. Не запускай параллельное редактирование одних файлов несколькими кодирующими агентами.

1. Выбери небольшую задачу из текущего этапа: требование, ограниченный набор файлов, ожидаемый результат и критерий проверки.
2. Прочитай затронутый код и контракт. Кратко опиши изменение; не начинай переписывать проект целиком.
3. Внеси согласованное изменение. Сохраняй публичные контракты и избегай лишних зависимостей.
4. Запусти проверки, соответствующие изменению: формат/контракт, целевые тесты, анализ типов/линтер или измерение нагрузки. Для безопасности, ретраев и преобразований нужны содержательные тесты, а не копия реализации.
5. Если проверка не прошла, устрани причину и повтори затронутую проверку. Не скрывай проблему удалением теста, ослаблением ожиданий или подменой измерений.
6. Передай результат: изменённые файлы, выполненные проверки и их фактический статус, оставшийся риск, следующий шаг. Не пиши «готово», если остаётся обязательная часть задачи.

При продолжении в новой сессии сохраняй короткую сводку: подтверждённые ограничения, решения с основаниями, текущий этап, последние команды проверок и результаты, открытые дефекты. Корневой `AGENTS.md` направляет к этим документам; в первой задаче проверь их фактическое чтение. Не загружай заново все исследования/PDF для каждой маленькой правки.

## 7. Измерения и сдача

- Отчитывайся отдельно по обнаружению, маскированию и восстановлению, а также по категориям и отрицательным примерам. Локальные precision/recall/F1 полезны для диагностики, но не заменяют неизвестный официальный evaluator.
- Для round-trip локально требуй точное равенство исходнику на каждом проверяемом случае, включая ретраи. Это инженерный критерий теста, не переопределение официального порога 95%.
- В отчёте нагрузки указывай железо, число workers/реплик, длительность, распределение размера входа, RPS предложенный/успешный, ошибки/429, p50/p95/p99/max, память, CPU и метод подсчёта токенов.
- Не выдавай 10-секундный таймаут за допустимую целевую задержку: исходное ТЗ требует ≤1 секунды, обновлённые критерии ориентируют на ≤0,5 секунды при 1000 RPS. Не обещай 1000 RPS по результатам проверки на одном коротком запросе.
- Сначала обязательная приёмка и качество, затем бонусы. Бонусы не разрешают откладывать покрытие категорий, безопасность или доступность.
- Упаковывай только разрешённые исходные материалы в ZIP без секретов, зависимостей, сборок и больших данных. Проверяй состав архива и запуск из чистого распакованного каталога.
- Готовность означает: проверенный код, доступный сервис, результаты обязательных автоматических проверок и своевременная сдача. При отсутствии официального результата честно указывай «локально проверено, официальный прогон ещё не пройден».
