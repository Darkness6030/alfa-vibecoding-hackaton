# Производительность 0.4.4 и воспроизведение

Измеряется реальный HTTPS `/process`: детекция, Redis, Fernet и INFO-логи включены. Каждый уникальный ID получает два последовательных запроса — маскирование и точное восстановление. RPS означает HTTP-запросы, а не пары. Все значения синтетические. Максимальная скорость коротких строк не переносится на большие документы.

## Среда и методика

Linux amd64, 8 логических CPU, 11,7 GiB RAM, 8 workers, admission 128 на worker. API ограничен 2 GiB, Redis — 1280 MiB, maxmemory 1024 MiB / noeviction, TTL 900 секунд. Nginx 1.28: TLS, HTTP/1.1 к upstream, keepalive 64, worker_connections 4096, rlimit_nofile 8192; память 128 MiB. На сервере работают ещё 24 контейнера.

Генератор throughput находится на том же сервере и конкурирует за ресурсы. Путь — host loopback через опубликованный HTTPS-порт Docker. Это эксплуатационное измерение общей среды, не независимый внешний нагрузочный стенд. Внешняя доступность, ожидаемые маски, повторные запросы и большие документы проверены отдельно с другого устройства.

Корпуса опубликованы в `benchmarks/`: `corpus-short.json` — 64 коротких RU/EN/mixed строки, до 95 байт до уникального суффикса; `corpus-mixed.json` — 8 документов по 470–836 байт, каждый содержит все 17 категорий, 20–21 сущность и отрицательные контексты. Ожидаемые маски второго корпуса проверены отдельными тестами. Сам по себе точный round-trip не доказывает полноту маскирования.

Open-loop генератор планирует новые пары независимо от завершения предыдущих. У каждой пары второй запрос следует после первого; направления в чистом прогоне равны. `successful_http_rps` учитывает полное время, включая завершение оставшихся запросов. Ошибки, 429, dropped_pairs и round_trip_failures считаются отдельно. Перцентили относятся к полученным ответам; 429 не выдаются за успешную обработку. QA-ramp — наша интерпретация ориентира 330 RPS с пиками 1000, не точная неизвестная кривая жюри.

После обнаружения пропусков исправлена передача управления циклу событий: даже опоздавший производитель даёт завершиться активным запросам. Регрессия с искусственной паузой 40 мс теряла 14 пар до исправления и 0 после. Новые отчёты дополнительно содержат максимальное опоздание подачи, число прибытий с задержкой свыше 10 мс и максимум активных пар. Пропуски старого генератора не удалены из отчётов и не пересчитаны задним числом.

Во всех завершённых парах восстановление точное. Короткий успех на 2000 не подтвердился длительным прогоном: устойчивые 2000 RPS не заявляются. В длинном прогоне максимальное опоздание производителя — 1,157 с, достигнут лимит 512 активных пар. Причина единственного 502 отдельно не установлена; OOM и рестарт API не наблюдались. Предшествующий пятиминутный 1000 RPS старым генератором дал 299828 успешных ответов, 0 HTTP-ошибок/429 и 86 пропущенных пар, поэтому также не считается чистым.

QA-ramp использовал исходный генератор и завершил все 49125 запланированных пар; дефект планировщика не привёл к потерям в этом прогоне. Максимальная задержка ответа — 232,28 мс. Это полезное измерение более насыщенных документов, но не гарантия всех размеров из ТЗ.

## Исправление HTTPS и внешние проверки

До исправления TLS-прокси минутный серверный прогон 1000 RPS дал 1183 таймаута и 12814 пропущенных пар. На том же API после keepalive и повышения лимитов: 60000 успешных ответов, 0 ошибок/429/пропусков, p99 27,09 мс, max 181,35 мс. Это диагностическая версия 0.4.3 с будущим конфигом 0.4.4. Отдельный внешний HTTPS-прогон после keepalive: 60000 успешных ответов, 0 ошибок/429/пропусков, p99 352,60 мс. Короткие и долгие тесты, внешний путь и loopback не смешиваются в одну оценку.

Финальная 0.4.4: 90 внешних HTTPS-сценариев / 360 запросов с ожидаемыми масками, повторами и восстановлением — PASS. Отдельно проверены protected proxy/metrics, запрет analytics, 413 для слишком большого chunked тела и безопасный 422 для неверного JSON.

Большой внешний HTTPS-запрос: 100005 технических пробельных токенов, 1325048 байт, маскирование 2,593 с, восстановление 5,917 с, точное совпадение. Это не токенизатор DeepSeek. В отдельном серверном испытании 0.4.3 плотный текст из 100000 email занимал 1,4 МБ, маска — 4,3 МБ; 2,221 / 0,208 с, exact. Алгоритмы детекции 0.4.3 и 0.4.4 совпадают. Ни задержка менее секунды для любых документов, ни 95% на неизвестном корпусе не заявляются.

## Воспроизведение

Сначала создать секреты и запустить Compose по README. Для похожего сервера установить 8 workers и 128 admission на worker; для другого железа подобрать ресурсы отдельно.

```sh
ALFAGEN_WORKERS=8 ALFAGEN_MAX_CONCURRENCY=128 docker compose up -d --no-deps api
python benchmarks/load_test.py --url https://127.0.0.1:18443 --rps 1000 --duration 300 --concurrency 512 --corpus benchmarks/corpus-short.json --output output/load-1000.json
python benchmarks/load_test.py --url https://127.0.0.1:18443 --rps 1000 --profile qa-ramp --duration 300 --concurrency 256 --corpus benchmarks/corpus-mixed.json --output output/load-qa.json
```

HTTPS требует TLS overlay из README. Для HTTP использовать основной опубликованный порт. Генератор допускает self-signed по контракту стенда; для реальных данных нужен закрытый контур и проверяемый сертификат. Генератор не имитирует все повторы официального evaluator; 429 → повтор проверяется интеграционными тестами.

Память Redis растёт с размером новых пар, частотой и TTL. noeviction сохраняет принятые пары, но при заполнении новые получают контролируемый отказ. Текущий демо Redis без persistence: рестарт теряет активные пары. Повышение RPS не заменяет расчёт ёмкости на рабочем корпусе. Сырые локальные результаты и исторические неудачные прогоны сохранены отдельно от исходников сдаваемого ZIP.
