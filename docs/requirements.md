- Критерии допускают вариации масок и экспертную оценку; систематический пропуск категории существенно снижает балл. Участник подтвердил самостоятельный выбор и описание алгоритма. Формула автоматической метрики по-прежнему неизвестна: экспертная допустимость токенов не доказывает конкретный автоматический балл.

Честные измерения засчитываются и при недостижении цели; обязательность официального нагрузочного прогона из ТЗ этим не отменяется. Обработка до 100 000 токенов без падения сохраняется. Источник: критерии, стр. 2–3.
- Шифрование таблицы соответствий в критериях оставлено усмотрению жюри, но исходное ТЗ требует шифрования. План сохраняет защиту состояния и не обещает нормативного соответствия отсутствующим стандартам.
- На время автоматической проверки участник разрешил отключить ограничения доступа. Это временный режим проверяемого API, а не повод убрать демонстрацию политик доступа или раскрыть админку/Redis/метрики всему Интернету.
- Сервер — `ssh Dental`, запуск по IP, Docker; на время тестирования разрешено остановить все существующие контейнеры. Это действие отложено до подготовленного развёртывания, сейчас выполнен только осмотр ресурсов.
- Локальные ML-модели допустимы внутри Docker. Защищённый банковский контур и стандарты не предоставлены. Наличие настроенной coding-модели не означает наличие разрешённого программного LLM API для демо-прокси; участник отдельно выбрал заглушку на текущий этап, она должна быть явно подписана.

Финальные критерии отдельно выделяют утечку реальных ПД во внешнюю LLM как провал ключевой функции, который перевешивает остальные достоинства. Маскируемый текст и восстановленный ответ авторизованному потребителю — разные границы: в схеме и демо необходимо ясно показать, что видит LLM, а что получает потребитель.

## Обязательный результат

Сервис защиты ПД между системой-потребителем и LLM: определить ПД, замаскировать запрос и демаскировать результат, сохраняя полезный смысл. Правила и сценарии должны расширяться без переделки сервиса. Нужны качественная идентификация, мало ложных срабатываний, настройка по потребителям, простое подключение, предсказуемые ошибки и отсутствие исходных ПД в технических данных. Источник: PDF, стр. 1–3.

**Условия допуска:** исходный код в ZIP с успешной автоматической проверкой качества **и** развёрнутое решение для обязательного нагрузочного тестирования. Одной демонстрации либо одного ZIP недостаточно. Источник: PDF, стр. 5.

## Точный контракт проверки

Источник: PDF, приложение A, стр. 6–7.

```http
POST /process
Content-Type: application/json
```

```json
{"payload": "строка", "payload_id": "идентификатор"}
```

Успешный ответ `200`:

```json
{"result": "строка"}
```

- Оба входных поля обязательны и имеют тип string; выходной `result` также string.
- Новый `payload_id`: `payload` содержит исходную строку, вернуть маску и сохранить соответствие.
- Обратный запрос: тот же `payload_id`, `payload` содержит ранее возвращённую сервисом маску, вернуть исходную строку.
- `payload_id` уникален для элемента в рамках прогона; значение коррелирует пару направлений.
- Один проверяемый endpoint для обоих направлений. Нельзя требовать от стенда дополнительных полей `mode`, `tenant_id` и т. п., отсутствующих в контракте. Это не запрет на отдельные служебные endpoints приложения.
- В спецификации перечислены `429`, `4XX`, `5XX`. Структура тела ошибок не определена; фраза «ответ всегда» требует уточнения для ошибок. Успешные ответы держать строго в указанном формате.
- HTTP и HTTPS поддерживаются, самоподписанный сертификат допустим, проверка использует `ssl_verify=false`. Это свойство стенда, а не отмена требования шифрования.
- `&lt;строка&gt;` в PDF — напечатанный placeholder, не значение, которое следует отправлять буквально.
- Пример маски на стр. 7: `Клиент И. И. И., паспорт 45** ****56`. Это единственный приведённый пример, не полная спецификация масок.

## Как проходит автоматический прогон

Источник: PDF, приложение B, стр. 8–9.

| Параметр | Точное содержание документа |
| --- | --- |
| Маскирование | Сравнение с эталонной маской: нормированное span-based расстояние Левенштейна в диапазоне [0..1] |
| Демаскирование | Сервис получает свою маску; результат сравнивается с исходной строкой датасета |
| Категории | Категории ПД из ТЗ, включая сложные предложения |
| Таймаут | 10 секунд на запрос; более долгий ответ считается неответом |
| Ретраи | До 2 на каждый запрос, до 3 попыток всего; требуется идемпотентность по `payload_id` |
| `429` | Допускается под нагрузкой, учитывается `Retry-After`, стойкая перегрузка попадает в метрики |
| Неуспех маскирования с `429` | Демаскирование этого элемента не запрашивается |
| Неуспех демаскирования с `429` | Учитывается; проверка продолжается |
| Остановка | После 5 невалидных запросов подряд; `429` не увеличивает и не сбрасывает счётчик; успешный ответ сбрасывает |
| Нагрузка по умолчанию | Все категории, примерно 5 минут, целевой RPS 1000; элементы датасета переиспользуются |
| Latency в описании прогона | ≤1 секунды названо ориентиром, не жёстким лимитом |
| Доступность | URL решения должен быть доступен на момент прогона |

На стр. 9 дан `https://process-test.holydev.space/process` для самопроверки **формата обмена**. Он не обещает проверку качества детекторов или предоставление эталонных масок. В рамках текущего разбора обращения к нему не выполнялись.

## Упаковка

Только ZIP разумного размера с исходным кодом в корне либо понятной структуре. Не включать объёмные датасеты, дампы, архивы, медиа, бинарники; `node_modules`, `.venv`, `venv`, `env`; `target`, `build`, `dist`, `out`, `bin`, `obj`; `.git`, `.idea`, `__pycache__`, `coverage`. Источник: PDF §7.1, стр. 5. Числовой лимит ZIP, чек-лист проверки кода и допустимый состав вспомогательных файлов не указаны.

## Дополнительные плюсы, не замена обязательным требованиям

Источник: PDF §6, стр. 4.

1. Токенизация/детокенизация либо замена синтетическими данными.
2. Настройка вида маскирования/токенизации по системе.
3. RPS 2000 при Latency ≤1 секунды.
4. Документы, удостоверяющие личность, кроме паспорта РФ.
5. Настраиваемое маскирование при сочетании нескольких однозначно определённых типов ПД; пример ТЗ: ПИН отдельно не маскировать, ПИН вместе с номером карты маскировать. Не превращать этот бонусный пример в глобальную политику по умолчанию без уточнения.

## Неоднозначности исходного ТЗ и принятый порядок их разрешения

Ответы Q4–Q8 разрешают самостоятельные инженерные решения; этот перечень фиксирует исходные риски, а не новые обязательные вопросы участнику. Токенизация выбрана в D04, ретраи/TTL — D05, заглушка — D06, открытый тестовый доступ и TLS — D07. Формула автоматической оценки и точный профиль нагрузки остаются неизвестными.

| --- | --- | --- |
