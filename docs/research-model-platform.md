## 2. Точная модель: факты, а не перенос свойств семейства

- Официальная карточка **DeepSeek-V4-Flash-0731 существует** в организации DeepSeek. Это финальный релиз Flash после preview; карточка описывает модуль спекулятивного декодирования DSpark.
- Для точного релиза описаны уровни `reasoning_effort`: `low`, `high`, `max`.
- Результаты автора: Terminal Bench 2.1 — 82.7, DeepSWE — 54.4. Агентные кодовые тесты выполнялись в DeepSeek Harness minimal, с `max`, `temperature=1.0`, `top_p=0.95`. Это **не измерение в Kilo и не гарантия результата хакатона**.
- Рекомендация карточки для локального инференса: `temperature=1.0`, агентный `top_p=0.95`; 384K output для high/max относится к локальному запуску, а не к доступному лимиту организаторского API. Не копировать это значение в Kilo.

Источник: [официальная карточка DeepSeek-V4-Flash-0731](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731), проверено 22.09.2026.

**Критичное различие checkpoint и alias.** В записи 31.07 DeepSeek сообщил о нативной поддержке Responses API у Flash-0731. Но запись **10.09.2026** сообщает, что на публичном API старые имена `deepseek-v4-flash` и `deepseek-v4-flash-vision-exp` временно маршрутизируются на **V4.1 Flash**. Поэтому инструкция «подключи любой deepseek-v4-flash» сегодня не подтверждает соблюдение регламента. Сохраняем уже настроенное подключение организаторов; не мигрируем на публичный endpoint и не подменяем модель последним Flash. Новые визуальные возможности V4.1 не приписываем 0731. [DeepSeek API Change Log, записи 31.07 и 10.09.2026](https://api-docs.deepseek.com/updates/).

### Что остаётся неизвестным у организаторского endpoint

Действительный размер контекста и ответа; rate limits; квота; цена; поддержка конкретных reasoning-параметров и протокола; надёжность tool calls; параллельность; скорость на этом сервере. Наличие 1M в описаниях семейства не является разрешением отправлять 1M в данное подключение. Точное backend-соответствие проверяется несекретной информацией организаторов/провайдера; ответ самой модели «я 0731» доказательством не служит. Это проверка окружения, а не повод откладывать планирование и подготовку проекта.

## 3. Kilo: учитывать поколение расширения

Публичная документация сейчас различает **новое расширение на CLI backend** и legacy. Локально подтверждена установленная **7.7.6** (`package.json`); пакет `dist/extension.js` содержит подключение к CLI backend и поддержку `kilo.jsonc`. Это соответствует новому поколению. Данная проверка читала только файлы установленного расширения, не пользовательские настройки. Активную версию в UI всё равно полезно записать для доказательств. Не обновлять рабочую среду посреди двухдневного хакатона только ради новых возможностей.

Локальные первичные источники: [package.json](/Users/darkness/.vscode/extensions/kilocode.kilo-code-7.7.6-darwin-arm64/package.json:5), [extension.js](/Users/darkness/.vscode/extensions/kilocode.kilo-code-7.7.6-darwin-arm64/dist/extension.js).

| Возможность | Подтверждённое поведение | Решение для хакатона |
|---|---|---|
| Инструкции | В текущей версии корневой `AGENTS.md` обнаруживается автоматически; дополнительные файлы можно подключить через `instructions`; локальные `AGENTS.md` загружаются при чтении файлов каталога | Короткие обязательные правила в корне; полное ТЗ читать по ссылкам. Проверить загрузку правил в первой сессии |
| Старые правила | `.kilocoderules` поддерживаются через миграцию, `.kilocode/rules/` — для совместимости | Если установлен legacy, пользоваться его существующим механизмом, не создавать несколько расходящихся копий |
| Режимы | Текущие custom agents — Markdown в `.kilo/agents/`; legacy использовал `.kilocodemodes`/`custom_modes.yaml` | Для одиночки достаточно Plan/Architect → Code → Debug, без собственного оркестратора |
| Модель режима | Custom agent может иметь `provider/model`; ручной выбор модели запоминается отдельно и способен отличаться от default | После переключения режима проверять точное разрешённое имя |

Источники: [Custom Instructions](https://kilo.ai/docs/customize/custom-instructions), [Custom Rules](https://kilo.ai/docs/customize/custom-rules), [Custom Modes](https://kilo.ai/docs/customize/custom-modes). Проверено 22.09.2026. Названия кнопок могут отличаться у установленного расширения.

**Tools и разрешения.** Kilo документирует чтение/изменение файлов, shell, поиск, web и делегирование; правила `allow`/`ask`/`deny` проверяются по порядку, последнее совпадение побеждает. Инструкция на естественном языке не заменяет разрешения инструментов. Практический профиль: чтение проекта и локальные проверки разрешены; секреты не читать; глобальные операции и деплой выполнять только в пределах согласованной задачи. При read-only ревью нельзя оставлять unrestricted shell: им тоже можно менять файлы. [Agent Permissions](https://kilo.ai/docs/customize/agent-permissions).

**Snapshots/checkpoints.** В текущем расширении включены по умолчанию; хранятся отдельно от Git проекта; откат UI выполняется к пользовательскому сообщению, не к отдельной правке внутри длинного ответа. Игнорируемые Git файлы не сохраняются; без snapshot возможен откат разговора без отката файлов. Поэтому один запрос — один проверяемый небольшой шаг, а пройденные этапы фиксировать обычными Git-коммитами. Историю сессий до сдачи сохранять. [Checkpoints](https://kilo.ai/docs/code-with-ai/features/checkpoints).

**Контекст и лимиты.** Для custom model Kilo имеет `limit.context`, `limit.output` и необязательный `limit.input`. У неизвестной каталогу модели отсутствие корректного контекста может отключить автоматическую компактизацию: значение по умолчанию `0`. `name` в интерфейсе и API-facing `id` могут различаться. Проверять реальные значения своего подключения, не угадывать их по названию. Не менять protocol/endpoint ради общей рекомендации документации. [Custom Models](https://kilo.ai/docs/code-with-ai/agents/custom-models).

**Сабагенты и смена моделей.** Документация говорит о наследовании модели родителя по умолчанию, но допускает отдельные overrides. Для хакатона проверить каждый используемый режим/сабагент; не включать Auto Model и автоматический fallback на другую модель. При переполнении контекста — новая задача с передачей состояния, не смена модели. [Model Selection](https://kilo.ai/docs/code-with-ai/agents/model-selection).

## 4. Рекомендуемый профиль работы — наши решения, не свойства модели

1. Сохранить рабочую настройку организаторов. В начале дня записать версию расширения и точное несекретное имя выбранной модели. Скриншот делать без API-ключей и заголовков авторизации.
2. Не создавать отдельную агентную инфраструктуру, MCP-серверы, внешнюю индексацию или локальный сервер этой LLM. Они не нужны для разработки небольшого Python/Docker API за два дня.
3. Начать с текущих параметров. Если endpoint поддерживает reasoning, использовать `high` для реализации и `max` только для сложного архитектурного разбора/диагностики; сравнивать время до результата. Не снижать температуру до 0 по привычке и не применять вслепую локальные параметры карточки к hosted API.
4. В каждый запрос включать цель, конкретные файлы, инварианты и критерии приёмки. Просить выполнить изменение и проверки, показать результат и остаточные ограничения. Не просить «написать всё приложение» одним сообщением.
5. В начале новой задачи читать `model-rules.md`, нужный раздел требований и краткое состояние последнего этапа. Не грузить все PDF и весь журнал многократно. Для требований использовать проверенную текстовую выжимку; PDF-картинки проверяет человек.
6. При двух неудачных исправлениях одной ошибки остановить наращивание патчей: новый Debug-контекст, минимальный воспроизводимый пример, фактический traceback и последний рабочий commit. Лимит «два» — наш организационный выбор.
7. Отделить LLM, создающую код, от алгоритма runtime: обязательная DeepSeek в Kilo не доказывает необходимость вызывать внешнюю LLM на каждом запросе обезличивания.

## 5. Ручной capability probe: 10–15 минут в Kilo, выполняет участник

Цель — проверить свою связку модель → endpoint → расширение. Это сценарии запросов, не готовый код. Подготовить отдельную тестовую папку/ветку; все исполняемые файлы для пробы создаёт только разрешённая модель через Kilo.

| Шаг | Что попросить/проверить | Успех |
|---|---|---|
| 1, 2 минуты | Посмотреть в UI версию, модель и известные лимиты. Не открывать секреты | Записаны версия расширения, имя модели, доступные параметры; неизвестные помечены |
| 2, 2 минуты | «Прочитай правила и требования. Назови контракт API, крайний срок и три запрета. Ничего не меняй» | Реальное чтение файлов и точные ответы, без выдуманных ограничений |
| 3, 3 минуты | «В тестовой папке создай минимальную Python-функцию обратимой подстановки и тест на кириллице; запусти тест» | Есть tool calls чтения/редактирования/shell; тест действительно запущен, виден exit code |
| 4, 3 минуты | «Добавь случай с одинаковым фрагментом дважды и emoji; сначала покажи результат теста, исправь при необходимости» | Сохраняется кодировка, реальный цикл диагностики, изменения локальны |
| 5, 2 минуты | Сделать небольшой отдельный Markdown-шаг и проверить checkpoint/откат только этого шага | Понятна гранулярность восстановления; рабочие файлы не потеряны |
| 6, 2 минуты | Создать новую задачу с короткой передачей состояния, снова проверить модель | Та же 0731, правила читаются, состояние восстановлено |

Записать в собственный журнал: дата, модель в UI, типы успешных tools, примерное время до результата, лимиты если известны, ограничения. Не записывать токены доступа или полный сетевой request. Тест не доказывает качество детекции ПД, предельный контекст, 1000 RPS или идентичность backend-весов; он подтверждает работоспособность рабочего цикла.

Если tool calls не работают: сохранить несекретный текст ошибки, уменьшить задачу до одного чтения, проверить объявленную поддержку tools/протокол по инструкции организаторов. Не обходить проблему кодогенерацией другой моделью. Если работает чтение/редактирование/терминал — сразу переходить к первому этапу проекта, не тратить день на настройку Kilo.
