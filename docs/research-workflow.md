## 2. Минимальная организация контекста

Kilo документирует загрузку корневого `AGENTS.md`, применение изменений в новых задачах и правила для каталогов. В актуальной документации прежний Memory Bank объявлен устаревшим. Достаточно одного короткого корневого файла с критичными ограничениями и ссылками на документы; отдельную систему памяти за два дня строить не требуется. Фактическую загрузку правил проверить в своей версии. [Kilo: AGENTS.md](https://kilo.ai/docs/customize/agents-md).

Kilo поддерживает project rules, но прямо оговаривает best-effort соблюдение. Правило в промпте не заменяет проверку результата. Актуальные docs описывают `instructions` в `kilo.jsonc` и совместимость с `.kilocode/rules/`; выбрать один работающий механизм, избегая нескольких противоречащих копий инструкций. [Kilo: Custom Rules](https://kilo.ai/docs/customize/custom-rules).

Рекомендуемое разделение содержания:

- Постоянные правила: точная модель, Python/Docker, контракт API, запрет открытых ПД в LLM и логах, обязательная обратимость, запрет выдумывать успешные проверки.
- `requirements.md`: источник истины о требованиях и критериях.
- `execution-plan.md`: порядок работ и условия завершения этапов.
- Краткая заметка передачи: последний проверенный commit, текущая задача, принятые решения, реальные ошибки, следующие действия.
- В текущей задаче: только релевантные файлы, один ожидаемый результат, несколько характерных примеров и условия приёмки.

Это адаптация принципа небольшого полезного контекста и сохранения состояния вне чата; опубликованный опыт Anthropic не гарантирует аналогичный эффект на точной DeepSeek. [Anthropic: Effective context engineering for AI agents, 29.09.2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

После завершённого компонента открывать новую задачу с заметкой передачи. Если доступно уплотнение контекста, проверять итоговую сводку: не исчезли ли контракт, модель, ограничения и незакрытые ошибки. Kilo предупреждает: для custom-моделей без объявленного размера контекста автоматическое уплотнение не работает. Также отдельная модель может быть настроена именно для compaction; проверить, что она не приводит к незаметному использованию другого провайдера. Не подставлять произвольный размер окна. [Kilo: Context Condensing](https://kilo.ai/docs/customize/context/context-condensing).

## 3. Рабочий цикл одной задачи: 25–50 минут

Указанные интервалы — практический бюджет участника, а не замер скорости модели.

1. **3–5 минут: постановка.** Выбрать одну вертикальную возможность: например, поведение повторного `payload_id`, а не «вся безопасность». Указать затрагиваемые файлы, вход/ожидаемый выход, ограничения, проверку.
2. **До 5 минут: короткий план.** Модель называет существующие точки изменения и проверки. Если контракт не меняется и задача уже согласована, выполнять без дополнительного круга утверждения.
3. **15–25 минут: реализация через обязательную модель.** Один поток изменений. Не запускать несколько кодирующих агентов в общей рабочей папке: одному участнику трудно своевременно проверить интеграцию.
4. **5–10 минут: проверка.** Прочитать diff, выполнить относящиеся к поведению проверки и один сквозной smoke. Отдельно проверить, что тесты не ослаблены ради зелёного результата.
5. **2–5 минут: фиксация.** Сохранить рабочий commit и короткую заметку: что реально проверено, какой результат, какой риск остался.

Подход «прочитать → спланировать → изменить → проверить» описан в инженерной публикации Anthropic; это перенос общей организации работы, а не использование команд Claude или предположений о его режимах мышления. [Anthropic: Claude Code best practices, 18.04.2025](https://www.anthropic.com/engineering/claude-code-best-practices).

**Правило остановки:** после двух неудачных исправлений одной ошибки прекратить расширять задачу. Попросить минимальный воспроизводимый случай, точную причину и одно исправление. Если за 20 дополнительных минут нет прогресса — вернуться к последней рабочей версии, вынести необязательную возможность из релиза. Для обязательной функции упростить подход и сохранить требуемое поведение.

Kilo snapshots/checkpoints полезны для отмены, но не заменяют Git. Актуальные docs предупреждают, что откат может вернуть только переписку, а не файлы, если snapshot отсутствует; игнорируемые файлы не включаются. После любого отката проверить diff и smoke. Удалённое состояние сервиса, данные хранилища и фоновые процессы проверять отдельно. [Kilo: Checkpoints](https://kilo.ai/docs/code-with-ai/features/checkpoints).

## 4. Что именно проверять в этом проекте

Это проектная программа проверки по локальным критериям, а не универсальный «процент покрытия».

- Для каждой из 17 категорий: характерный пример, вариация написания, похожий нечувствительный текст. Не заявлять 95% по собственным трём примерам.
- Полная цепочка: исходный текст → защищённый текст → обратное восстановление, включая Unicode, пунктуацию, повторяющиеся и пересекающиеся сущности.
- Ретраи: одна и та же исходная строка; повтор обратного запроса; конфликтующий текст при том же ID; параллельное обращение к одному ID; истечение состояния.
- Авторизация/политики: разрешённая система, запрещённая, запрет обратного преобразования, разные настройки типов. Открытый режим для проверяющей системы — отдельная явно документированная конфигурация.
- Контекстные ловушки: Пушкин как поэт, публичный адрес отделения и адрес клиента; публичное имя не должно превращаться в глобальный обход для совпавшего имени клиента.
- Утечки: проверить фактический outbound-запрос к LLM, текст ошибок и журнал. Модель не может подтверждать отсутствие утечки только по намерению функции.
- Большой текст: отдельная проверка предельного размера; нагрузка короткими текстами — другой эксперимент. Для результатов фиксировать железо, размер запросов, конкурентность, длительность, p50/p95/p99, ошибки, throughput и используемое определение TPS.
- Новый запуск из чистого состояния по README; доступ к URL извне; восстановление после рестарта в соответствии с описанным временем хранения.

Сначала синтетические примеры. Часть примеров участник держит отдельно до проверки результата, чтобы модель не оптимизировалась только под известные строки. Для трудных решений запросить чтение diff в новой задаче той же обязательной модели; генерация тестов и исправлений остаётся у неё.

Промпты ниже содержат инструкции, не программный код. Перед использованием подставить реальные файлы и условия.

### Старт и проверка контекста

> Работаем в Kilo Code через DeepSeek-V4-Flash-0731 организаторов. Прочитай docs/model-rules.md, docs/requirements.md, docs/execution-plan.md и актуальные ответы docs/questions.md. Затем предложи первую задачу на 30–45 минут с наблюдаемой проверкой. Код и тесты создавай только в этом рабочем процессе обязательной модели.

### Реализация одной возможности

> Задача: [одно поведение]. Критерий жюри: [пункт]. Прочитай [файлы]. Вход/ожидаемый результат: [примеры]. Сохрани [инварианты]. Область изменения: [компонент]. Коротко назови план и выполни его, если нет конфликта требований. Добавь проверки поведения и запусти их. Не переписывай соседние компоненты. В отчёте укажи изменённое поведение, реальные команды и результаты, оставшиеся ограничения. Не отмечай задачу выполненной при пропущенной проверке.

### Исправление ошибки

> Наблюдаемая ошибка: [результат]. Ожидалось: [результат]. Воспроизведение: [шаги/синтетический ввод]. Последний рабочий commit: [hash]. Сначала локализуй причину по исходникам и фактическому выводу, затем исправь минимально. Не ослабляй проверку и не меняй контракт. Если причины не установлены, явно обозначь гипотезы и проведи одну различающую проверку.

### Независимое чтение результата

> Проверь [diff/commit] по требованиям [пункты]. Сейчас ничего не изменяй. Ищи только воспроизводимые проблемы: утечки, нарушение контракта, неверное восстановление, гонки ID, регрессии политик и непроверенные утверждения. Для каждой находки укажи сценарий, файл и наблюдаемый эффект. Отдельно перечисли проверки, которые не выполнялись.

### Завершение сессии

> Запиши краткую передачу состояния: последний проверенный commit, завершённые возможности, выполненные проверки с результатами, нерешённые ошибки, принятые решения с причинами, точная следующая задача. Не копируй весь чат. Не включай секреты или исходные ПД. Новая сессия должна продолжить работу по этой заметке и документам проекта.

В дальнейших пунктах «прокси с LLM» сейчас означает явно подписанный mock за заменяемым адаптером; живой внешний вызов не является блокером текущей реализации и не объявляется проверенным. ## 7. Приоритеты именно по критериям жюри

Источник: локальные `критерии_оценивания_альфа.pdf` и `критерии_фрейм_топы.pdf`, прочитаны полностью 22.09.2026.

- Идентификация/маскирование, восстановление и точность — **13 из 30 баллов**. Утечка при демо особенно опасна: финальный экспертный лист называет её провалом ключевой функции.
- Конфигурация/расширяемость — **4 балла**, причём отсутствие README обнуляет критерий. README вести с первого рабочего запуска.
- Производительность — **4 балла**; ориентир критериев **≤0.5 с при 1000 RPS**. Честные измерения ценятся даже без полного нагрузочного теста. Не жертвовать обратимостью ради неподтверждённых 2000 RPS.
- Безопасность/логи/метрики — **3**, дополнительные сценарии — **3**, демо — **3**. Токенизация уже может быть дополнительным сценарием: показать её пользу и работу, не создавать бонусы лишь ради количества.
- Production-готовность явно не оценивается. Нужен рабочий демо-прокси, а не многосервисная платформа с долгой интеграцией.

Скринкаст должен за короткое время показать: задачу и схему; исходный синтетический текст; фактический безопасный LLM-запрос; корректное восстановление; контекстную ловушку; изменение политики без кода; реальные метрики; одно ограничение. Подготовить объяснение архитектуры на 1–2 минуты и проверять, что все цифры в презентации относятся к сдаваемой версии.
